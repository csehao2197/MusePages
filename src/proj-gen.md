## Goal

Create MusePages (https://musepages.com), a static gallery showcasing the front pages of Next.js projects generated by AI models. The current root `out` folder is the deployable website and the accepted visual baseline for further development.

## Requirements

1. Keep website source code, prompt Markdown files, gallery metadata, and generation workflows under `src`. Keep deployment scripts and configuration under the root `deploy` folder, and local SSH keys under the Git-ignored root `key` folder. The `out` folder is generated build output, not a source folder; do not maintain its files manually.
2. Keep the complete deployment in the root `out` folder. When source code, prompts, metadata, or assets change, regenerate the affected pages, screenshots, and gallery together. The complete regeneration workflow is still to be implemented; the existing sample command does not regenerate the whole website.
3. Generate the overall gallery at `out\index.html`, not at the repository root or inside an individual project's export folder. Use a responsive collection of square tiles, one per generated result. Each tile must display a screenshot image of its generated front page, a link to the actual front page, and a separate link to its original prompt. Show its title, inherited style tags, and AI model without overwhelming the image. Use static preview images, not embedded live pages.
4. Keep all exported pages under `out\pages`, organized by prompt. The current deployment has one front page per prompt, directly in its prompt folder. Preserve these working URLs. When a prompt gains multiple results, give additional results unique subfolders and their own gallery tiles without overwriting existing results.
5. Copy each prompt Markdown file into its corresponding output folder alongside its generated results, and link to it from the gallery.
6. Assign each prompt project one or more tags describing its visual style, such as minimalist, modern, retro, or brutalist. Each generated front page inherits all tags from its prompt project and also has a tag identifying the AI model that generated it.
7. Preserve each project's front-page appearance and client-side behavior in the static export, including the required CSS, JavaScript, images, fonts, and other supporting files. Use asset paths that resolve within each result's deployed subfolder. Link explicitly to `index.html` for front pages and gallery return links; do not rely on a host automatically opening directory indexes.
8. Host only the gallery, prompt Markdown files, exported front pages, and their supporting files, not the full generated websites or project source code. No Next.js server or server-side runtime runs on the hosting site.
9. Deploy the entire root `out` folder as the document root of https://musepages.com. The future full-site workflow must refresh changed results and remove output only for results intentionally removed from the source; generating one sample must not remove or hide other published pages.

### Gallery Appearance and Navigation

Preserve the current warm off-white background, dark green text and actions, serif display headings, compact introduction, and rounded square cards. The grid uses three columns on desktop, two at widths up to 1000 pixels, and one at widths up to 650 pixels.

Each tile contains a linked screenshot, a sample or demo badge, the prompt number and category, a linked page title, style and model tags, and separate **View page** and **Read prompt** links. Screenshots are static `preview.png` files, not live iframes. Current screenshots are 1200 by 900 pixels and are cropped from the top to fit the image area inside each square tile.

Use explicit file links such as `pages/001-destination-guide/index.html`, not just `pages/001-destination-guide/`. Return links from that page use `../../index.html`. This supports hosts that display directory listings instead of opening `index.html`.

## Existing Generation Command and Limitations

`npm run generate:sample` copies the gallery template and illustrative Tokyo page from `src\gallery`, copies prompt 001, and refreshes that page's `preview.png` using the existing Playwright Chromium installation. It does not run a Next.js build.

This command only generates page 001 and replaces `out\index.html` with the sample gallery template. It does not assemble pages 002-004 or their screenshots. Do not use it as a full-site refresh or overwrite the accepted four-page catalog with a sample-only gallery.

The full-site `npm run build` command is a future requirement, not a currently available root script. It must assemble all published results, their prompts, assets, screenshots, and the complete gallery from source.

## Hosting and Verification

Serve the root `out` folder over HTTP or HTTPS, including for local previews, and open `/index.html`. Opening files directly through `file://` is not the supported preview method. Hosting requires only a static file server, not a Next.js runtime.

Check square card layout and readable actions at desktop and mobile widths, and test navigation without automatic directory-index handling. The existing focused regression tests run with `node --test src\workflows\generate-sample.test.mjs`; they cover sample generation and explicit page/return links on a directory-listing host. They do not validate the entire deployed collection.

## Deployment SSH Key Setup

From `C:\Code\MusePages` in PowerShell, create an Ed25519 key pair if one is not already available:

```powershell
New-Item -ItemType Directory -Path .\key -Force | Out-Null
ssh-keygen -t ed25519 -f .\key\musepages
```

For a key without a passphrase, press Enter at both passphrase prompts. Do not overwrite an existing key unless intentionally replacing it; replacement requires installing the new public key on the server.

The private key is `key\musepages` and the public key is `key\musepages.pub`. The root `/key/` folder is Git-ignored. Keep the private key local, outside `out`, and never commit or upload it. An unencrypted private key can be used by anyone who obtains it, so protect access to the folder.

Copy only the public key's contents:

```powershell
Get-Content .\key\musepages.pub | Set-Clipboard
```

In an existing Debian root session, prepare the SSH folder and edit the authorized keys:

```bash
mkdir -p /root/.ssh
chmod 700 /root/.ssh
nano /root/.ssh/authorized_keys
```

Paste the public key as one complete new line, preserving existing keys. Save with Ctrl+O, Enter, and exit with Ctrl+X, then set permissions:

```bash
chown root:root /root/.ssh /root/.ssh/authorized_keys
chmod 600 /root/.ssh/authorized_keys
```

Keep the existing server session open while testing key-only login from PowerShell. Replace `YOUR_SERVER_IP` with the server address:

```powershell
ssh -i .\key\musepages -o IdentitiesOnly=yes -o PasswordAuthentication=no -o KbdInteractiveAuthentication=no root@YOUR_SERVER_IP "echo 'Key authentication succeeded'"
```

## Deployment Configuration and Commands

The current `deploy\config.json` contains:

```json
{
  "server": "45.76.249.37",
  "loginId": "root"
}
```

`deploy\deploy.ps1` combines those values into `root@45.76.249.37` and uses `key\musepages` as its default private key. The remote website folder is `/var/www/mywebsite.com/html`, currently set in the script rather than the JSON configuration. The existing remote website folder must be present before deployment.

Requires Windows OpenSSH (`ssh` and `scp`), a Debian-compatible remote shell and utilities, and a remote account with write access to `/var/www/mywebsite.com`. Install the matching public key in the remote account's `authorized_keys` before deploying. Only the contents of `out` belong on the website; keys, deployment configuration, and project source are not uploaded.

From the repository root, preview the operation, then deploy:

```powershell
.\deploy\deploy.ps1 -WhatIf
.\deploy\deploy.ps1
```

`-WhatIf` describes the operation without connecting to the server or changing remote files. The script resolves its default source, key, and configuration paths relative to its own location, not the current working directory.

Override the destination or private key for a single deployment when necessary:

```powershell
.\deploy\deploy.ps1 -Server root@YOUR_SERVER_IP -PrivateKey C:\Keys\musepages -WhatIf
```

### Backup-First Deployment Behavior

1. Check that the local `out\index.html` and private key exist and SSH/SCP commands are available.
2. Connect over SSH and move the existing remote `html` folder to `/var/www/mywebsite.com/html-backup-<timestamp>-<unique-id>`. If backup fails, stop without starting the upload.
3. Upload the local `out` folder over SCP directly as the new remote `html` folder, without an extra nested `out` directory. This replaces the complete website rather than merging with stale files.
4. Confirm remote `html/index.html` exists and set static-file permissions so the web server can read the deployment.
5. If upload or final permission setup fails, attempt to move any incomplete upload to `/var/www/mywebsite.com/html-failed-<unique-id>` and restore the backup as `html`. Report a separate error if automatic restoration also fails.

The website is briefly unavailable between moving the live folder and completing the upload. Backups remain on the server after successful deployment; the script does not automatically delete them. If rollback is needed, the backup folder is moved back into place rather than retained as an additional copy. Do not run overlapping deployments.

The script does not generate keys, rebuild the website, reload Nginx, or change its configuration. Nginx does not need a reload when only the website files change.
